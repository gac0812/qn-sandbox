# 07 — 文档规范与 ADR 流程

状态：Draft · 2026-10-24

## 1. 文档分层（谁写、谁读、何时更新）

| 文档 | 回答什么问题 | 更新时机 |
| --- | --- | --- |
| `README.md` | 这是什么、怎么装、怎么跑 | 用户可见行为变化时 |
| `AGENTS.md` | AI 在仓库里怎么干活 | 工作方式/红线变化时 |
| `docs/spec/*` | 产品边界、架构、规范细则 | 对应决策变化时 |
| `docs/adr/*` | 为什么当时这么定 | 有新决策/推翻旧决策时 |
| `crates/*/README.md` | 本 crate 职责、port 清单、用例、非目标 | crate 行为变化时 |
| `CHANGELOG.md` | 版本间变化 | 每次合并 |
| `docs/patches/*` | 对上游补丁的说明 | subtree 补丁变化时 |
| `docs/dev-notes/*.md` | 调研笔记（spike 产出，允许粗糙） | 随调研 |

规则：**文档与代码同 PR 更新**——改了行为不更新对应文档，验收不过。
文档里的事实（端口、路径、命令）改动必须 grep 全仓库文档同步，防漂移。

## 2. 写作规范

- 语言：规范/文档正文中文；专有名词、API 名、命令保持英文原文。术语以 `glossary.md` 为准。
- 每份 spec 顶部：`状态（Draft/Accepted/Deprecated） + 日期`；过期规范改状态并在正文顶部注明替代文档，不删除。
- 例子必须可复制执行（命令带平台标注：macOS / Windows）。
- 图用 Mermaid（CI 可渲染），不贴截图说架构。

## 3. ADR（架构决策记录）

### 何时必须写 ADR
- 新增/更换架构级依赖（RPC 框架、运行时、虚拟化技术、MCP SDK）
- 新增或改变 port（trait）的语义
- 新增平台后端
- 改变目录/crate 结构、依赖方向规则
- 推翻任何已有 ADR

不需要 ADR 的：crate 内部实现选择、bug 修法、测试用例增删。

### 流程
```
Proposed（AI/人起草，含选项对比与推荐）
  → 用户确认 → Accepted（附日期）
  → 被 new ADR 替代 → Superseded by NNNN（原文保留）
```

### 模板（`docs/adr/0000-template.md`）
见模板文件本体；核心要求：**选项至少两个、对比维度固定**（复用度/平台覆盖/维护成本/风险）、结论必须有依据而不是"感觉"。

### 编号与索引
- 编号四位递增，不重用；`docs/adr/README.md` 维护索引表（编号/标题/状态/日期）。
- AI 在完成任务时若发现现实与某 Accepted ADR 冲突：停下，起草新 ADR 或提 issue，**不得静默偏离**。

## 4. AI 生成文档的特别要求

- 禁止空洞的"综上所述/总而言之"式段落；每个段落要么有信息增量，要么删掉。
- 规范条款必须可判定（能回答"这条违规了吗"）；写不出判定方法的条款不要写。
- 表格优先于长段落；一屏内能扫完的规则才有人遵守。
- 引用外部项目时给链接与当时观察到的版本/日期（生态会变）。
