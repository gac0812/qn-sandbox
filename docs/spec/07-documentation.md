# 07 — 文档规范

状态：Draft · 2026-10-24 · 本版已移除独立 ADR 机制（决策记录方式见 §3）

## 1. 文档分层（谁写、谁读、何时更新）

| 文档 | 回答什么问题 | 更新时机 |
| --- | --- | --- |
| `README.md` | 这是什么、安全不变式、目标架构（guardrails 内容为准） | 产品定位/不变式变化时 |
| `CONTRIBUTING.md` | 人类协作：分支/评审/安全规则（#2 所有） | 队友维护 |
| `AGENTS.md` | AI 在仓库里怎么干活 | 工作方式/红线变化时 |
| `docs/spec/*` | 产品边界、架构、规范细则 | 对应内容变化时 |
| `crates/*/README.md` | 本 crate 职责、port 实现、用例、非目标 | crate 行为变化时 |
| `profiles/*/README.md` | 该 profile 的权限范围与凭证绑定 | profile 变化时 |
| `CHANGELOG.md` | 版本间变化 | 每次合并 |
| `TODO.md` | 工程待办（触发条件+验收标准） | 随任务 |
| `docs/dev-notes/*.md` | 调研笔记（spike 产出，允许粗糙） | 随调研 |

规则：文档与代码同 PR 更新——改了行为不更新文档，验收不过；文档中的事实（命令、路径、版本）变更必须全仓 grep 同步，防漂移。

## 2. 写作规范

- 语言：规范正文中文；专有名词、API 名、命令保持英文；提交与 PR 一律英文（CONTRIBUTING 要求）。术语以 `glossary.md` 为准。
- 每份 spec 顶部：`状态（Draft/Accepted/Deprecated）+ 日期`；过期规范改状态并注明替代文档，不删除。
- 例子必须可复制执行（标注平台：macOS / Windows）。
- 图用 Mermaid，不贴截图讲架构。

## 3. 重大决策记录（不设独立 ADR 目录）

- 承载方式：**GitHub issue + 对应 spec 同步修订**。决策 issue 模板要素：背景 / 选项（≥2，含否决理由）/ 结论 / 重审条件；结论落地时必须同步改受影响的 spec（在 spec 内以普通条文呈现，注明来源 issue 链接）。
- 必须走决策 issue 的：架构级依赖（安全内核、RPC 框架、GUI 框架）、port 语义变更、平台机制变化、推翻已有结论。
- 不需要的：crate 内部实现选择、bug 修法、测试增删。
- AI 发现现实与 spec 冲突：停下开 issue，**不得静默偏离**；spec 修订完成前按现行 spec 执行。

## 4. AI 生成文档的特别要求

- 禁止空洞总结段；每段要么有信息增量要么删掉。
- 规范条款必须可判定（能回答"这条违规了吗"）。
- 表格优先于长段落；引用外部项目给链接与观察日期。
